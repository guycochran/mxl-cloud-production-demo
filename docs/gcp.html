Running MXL on GCP — a portability proof

✅ Verified 2026-09-15

The scripts/quickstart.sh path ran clean end-to-end on a fresh GCP n2-standard-8 (us-west1-a, Ubuntu 24.04, AVX-512): MXL switcher ON AIR, keyer lower-third rendering, live CUT control, full flow set in /dev/shm/mxl/domain_1, WebRTC program in the browser. The same one command that works on Azure works on GCP — portability proven.

By Guy Cochran · Office Hours Global$300 free-credit windowSource: GCP-BUILD-PLAN.md

Why bother — and the honest framing

The MXL/TAMS switcher has nothing Azure-specific in it: an AVX-capable Xeon, a big /dev/shm, libfabric over TCP, cloudflared, ffmpeg. If it runs on Azure and AWS, it runs on GCP. Standing it up on GCP once — screenshot it, tear it down — is a cheap, strong data point: "the open standard doesn't care whose cloud you're on." Not a permanent home; a proof.

The cost warnings (on a $300 budget)

$300 is generous for a proof, tight for always-on. n2-standard-32 ≈ $1.55/hr, n2-standard-8 ≈ $0.39/hr → the pair is ≈ $1.94/hr — ~150 hours of 24/7, or weeks of deallocate-when-idle sessions. A 2-day build + first show is ≈ $55–60.

Same trap as AWS

Never send a raw v210 fabric flow across a zone or the internet — one 1080p30 flow is ~1.3 Gbps ≈ 585 GB/hr, and GCP inter-zone egress is ~$5.85/hr per flow. Put both hosts in the same zone (intra-zone internal-IP traffic is free). Credits expire — do the run, capture it, tear down.

The one real blocker: the global CPU quota

Confirmed in practice: the gate is not the regional quota — it's the global CPUS_ALL_REGIONS cap, which defaulted to 12 on a just-upgraded account. A 32+8 = 40 vCPU rig is blocked with Quota 'CPUS_ALL_REGIONS' exceeded. Limit: 12.0 globally.

  • Free-trial accounts can't request increases (capped at 8 cores). An upgraded account can.
  • Action: Console → IAM & Admin → Quotas → filter "CPUs (all regions)" → request 48. Upgraded accounts usually auto-approve in minutes (ours went 12→48 in ~1 min).
  • The fallback proof is already done: the full keyed switcher runs under 8 vCPU, so portability is proven now; the 32-core rig only adds headroom for two cameras + multiview + guests.

Per-host software builds (identical to Azure/AWS)

Nothing changes below the instance layer — that's the whole point. Ubuntu 24.04, MXL SDK + mxl-fabrics-demo, libfabric ≥ 2.x, ffmpeg, cloudflared. Verify grep avx /proc/cpuinfo first (N2 → yes). Build gotchas found (missing from the fabric handoff doc): git clone + bootstrap vcpkg at ~/vcpkg first (the preset hardcodes that path), and there are no build presets — build with cmake --build build/Linux-GCC-Release -j$(nproc), not --build --preset.

Field notes from the real-camera run

Achieved (all verified): a real studio PTZ (PTZOptics F63) and a Makito X4 encoder, both repointed Azure→GCP over SRT, landed live in the GCP domain — the Makito held 13+ min stable at 12.7 Mbps. The selector cut 4 real inputs; its output flow carried the live PTZ frame.

  • Selector requires a uniform grain rate. A PTZ pushing native 1080p60 lands as a 60/1 flow and the selector rejects the set (grain_rate 60/1 ≠ 30/1). Normalize on ingest with videorate ! video/x-raw,framerate=30/1.
  • SRT latency for WAN: the Azure 20 ms (tuned for ~6 ms studio↔VM LAN) was too tight for the studio→GCP-Oregon internet hop; 200 ms made both feeds hold.
  • Real PTZ → GCP over SRT works. The camera's built-in SRT sender is the optimized path (no ffmpeg transcode hop). One publisher per stream name.
  • Never hot-reconfigure the live selector. Repeatedly reconfiguring it littered /dev/shm with 45 stale flow dirs → frozen program. A reboot + one ordered bring-up = clean 8-flow domain.

The one open bug (honestly)

mxl2webrtc WHIP egress on the minimal quickstart — reproduced ~10× across reboots. Upstream is perfect (cameras land, selector/keyer/encoder run, domain clean), and the encoder logs WHIP handshake complete, but the browser gets stream not found — mediamtx never serves the path. The Azure rig avoids this because it runs the full backend + /api/mxl/repair orchestration, which the minimal quickstart lacks. Fix path: replicate the full bring-up-mxl.sh + backend (the AWS recorded build), don't hot-reconfigure the minimal quickstart.

That honesty is the point of a field note — portability is proven, and the remaining rough edge is documented so the next person skips the hours we spent on it.
