Reproducibility · AWS

Running MXL on AWS

Run the facility we proved on Azure for IBC 2026 — uncompressed v210 shared-memory switching, multi-host MXL fabric, guest SRT contribution, TAMS recording, public WebRTC — as a production deployment on AWS. Everything in the repo runs unchanged; only the infrastructure vocabulary translates.

By Guy Cochran · Office Hours Global~1–2 day replay of a 6-day discoverySource: AWS-BUILD-PLAN.md

Verified · Oct 2026 — this is no longer hypothetical

We built it. The entire switcher — not just the fabric leg — ran end-to-end on 2× c5n.9xlarge in us-west-2, fed by the real studio cameras (a PTZ and a Haivision Makito X4) pushing SRT across the public internet, straight from this repo plus the stock cbcrc images and Jonas Ohland's mxl-fabrics-proxy. Measured on air: both cameras 30.00 fps over cross-WAN SRT; cross-host program 31.3 grains/s at 3.99 ms p50 over the fabric; live cuts between the PTZ, a playout clip and the Makito. Those numbers reproduce the Azure fabric run almost exactly — the whole facility is cloud-portable. See the proof and the two honest caveats → (§7.5). (The run used the compute-optimised c5n for its 100 Gbps networking; the sizing below is tuned for a cost-balanced standing facility.)

The cost warnings that actually matter

The one that bites

Cross-AZ data transfer will eat you alive. An MXL fabric flow is ~1.3 Gbps of uncompressed v210 — ≈585 GB/hour, continuously. Same-AZ private-IP traffic (including over VPC peering) is free. Cross-AZ is ~$11.70/hour per flow; a raw flow at a public IP is ~$52/hour. Put Host 1 and Host 2 in the same AZ. Non-negotiable.

  • Viewer egress is fine. Each WebRTC viewer is ~5 Mbps ≈ $0.20/hr. A booth crowd costs beer money, not rent.
  • Stop instances when idle. EC2 stop keeps the EBS volumes and drops compute to zero — same discipline as the Azure deallocate rule.
  • Ballpark production rate (2 hosts, us-west-2, on-demand): m6i.8xlarge $1.536 + m6i.2xlarge $0.384 ≈ $1.92/hr + viewer egress.
  • New-account quota: fresh accounts often cap on-demand vCPUs at 32. File a quota increase to 48 vCPU on day 0 — it can take a day to approve and gates the whole build.

Network design — two VPCs (production + contribution DMZ)

Guests are strangers with a QR code. Their landing zone gets its own VPC: a compromised contribution host has no route to the program chain except the two fabric ports we explicitly peer. This is the broadcast ingest-DMZ pattern, in cloud vocabulary.

  • Peering: same region, same AZ — pick the AZ by ID (e.g. usw2-az1) since AZ letters shuffle per account.
  • Security groups use CIDR rules (cross-VPC SG references don't work over peering). Guests hit UDP 8890 on the DMZ; only fabric TCP crosses the peering.
  • Jumbo frames: MTU 9001 works within a VPC but peering clamps to 1500 — our Azure rig ran 1500 at 1.3 Gbps without complaint.
  • Elastic IPs on both hosts (stable SRT/WebRTC targets; free while attached). cloudflared needs no inbound.

Per-host software builds (identical to Azure)

Ubuntu 24.04 everywhere. The recipe is bring-up-mxl.sh plus:

  • libfabric ≥ 2.x from source (distro 1.x lacks FI_SOCKADDR_IP)
  • mxl v1.1.0 with -DMXL_ENABLE_FABRICS_OFI=ON (gotcha: shallow vcpkg clones fail baseline resolution — git fetch --unshallow)
  • Docker + the easy-mxl container suite (selector, HTML5 keyer, file player, mxl2webrtc, hls2mxl)
  • mediamtx, this repo's tools/ (ingests, layout compositor, audio, thumbs, grain_probe.py, guest-leg doctor, multiview), and cloudflared

The domain stays at /dev/shm/mxl/domain_1. Nothing in the data plane knows or cares which cloud it's on — that's the demo's thesis.

Build phases

  • Phase 0 — account prep (day 0, async): vCPU quota request, both VPCs + same-AZ-ID subnets + peering + SGs, 2× EIP, S3 bucket + gateway endpoints, IAM instance roles.
  • Phase 1 — single-host production (½ day): launch m6i.8xlarge, run the build. Success = test-pattern program over WebRTC + cuts working.
  • Phase 2 — contribution DMZ + fabric (½ day): launch m6i.2xlarge in the DMZ (same AZ ID!). First test: iperf3 across the peering — ≥4 Gbps and sub-ms RTT confirms same-AZ; ~1 Gbps + 1–2 ms means you crossed AZs, fix first. Expect the logged numbers: 30 grains/s, ~1080 slices/grain, ~1.3 Gbps/flow.
  • Phase 3 — TAMS on real S3 (½ day): segments to native S3 presigned URLs; the clipper works unchanged.
  • Phase 4 — hardening (½ day): grain probe, health board, guest-leg doctor, and flow_stabilizer.py deployed from day 1.

What we'd do differently (lessons pre-paid on Azure)

  1. Start at 32 vCPU. We resized D8→D16→D32 chasing headroom; the full rig idles around load 10–13 on 32 cores. Size for the end state.
  2. Deploy in dependency order and don't churn writers. Most of FINDINGS is one lesson: MXL readers die when a writer recreates its flow. Deploy flow_stabilizer.py from day 1 instead of retrofitting under fire.
  3. Same-AZ private IPs for all continuous flows (also the cost rule).
  4. Keep grain_probe.py running from day 1. Rate checks lie; only unique-frames/sec catches a repeat-wedged reader.
