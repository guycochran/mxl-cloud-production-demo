What is MXL (Media eXchange Layer)?

MXL is an open-source SDK for high-performance, container-friendly shared media exchange across on-premise or cloud environments. In plain terms: it lets software media functions share uncompressed video and audio through shared memory instead of passing it down a chain of boxes or copying it across a network.

What MXL actually is

Per its own SDK, "MXL is an open-source SDK designed for high-performance and container-friendly shared media exchange across on-premise or cloud environments." It's implemented in C++ (with a C API and Rust bindings), released under the Apache 2.0 licence, with its first alpha in June 2025. It's the data plane of the EBU's Dynamic Media Facility vision — the part that actually moves the pixels between software components.

The core idea is almost boring, which is why it's powerful: put the media in a shared-memory region, and let any media function (a switcher input, a keyer, a multiviewer) read and write it directly. No capture cards, no SDI router, no re-encode between stages.

The problem it solves

Traditional broadcast is a signal chain: camera → router → switcher → keyer → encoder, each a box that owns one stage. It's rigid, and every consumer of a source is another physical copy — another SDI run, another ST 2110 flow, another NDI stream to decode. Scaling costs grow with every tap.

MXL removes the wire between stages. When media lives in shared memory, the tenth consumer of a camera is a pointer, not a tenth copy. A multiviewer reading nine sources decodes nothing — it reads the same grains the program cuts. That single change is what makes a software-defined control room practical instead of just possible. Grains, flows and domains

Three words carry most of MXL's model (defined fully in the glossary):

  • Grain — one timestamped unit of media: a video frame or a block of audio. Grains carry a time, so position is a timestamp, not a queue slot.
  • Flow — a continuous sequence of grains of one type (a camera's video, say), held as a ring in shared memory.
  • Domain — the shared-memory region where flows live. A function joins the domain and immediately sees every flow in it. The domain is the router.

Grains being time-indexed has a quietly huge payoff for multi-host work: if two machines are clock-synced, a flow arriving over the network reads like a local one, with no manual offset — something we measured directly in the field findings.

Flow API vs Fabric API

The SDK exposes two APIs, and the distinction matters:

  • Flow API (from v1.0) — "Enables shared-memory access for zero-copy media workflows." This is the single-host case: functions sharing a domain in local memory.
  • Fabric API (from v1.1) — "Enables memory sharing through controlled data movement." This is how a domain extends across hosts — grains written on one machine appear in another's shared memory over the network (built on libfabric/OFI, with providers like tcp, verbs, shm and efa).

In practice we carried a live 1080p30 flow host-to-host over the Fabric layer at 30 grains/s with the receiving host's CPU essentially idle — the numbers are in the findings.

MXL vs NDI vs ST 2110 vs SRT

These are often lumped together as "ways to move video," but MXL is a different category. The honest distinction:

TechnologyCategoryFan-out costScope
MXLShared-memory media planeZero-copy — extra readers are pointersOne host (Flow API); multi-host via Fabric API
SMPTE ST 2110Networked uncompressed IP transportEach receiver is another flow on the wireFacility LAN / WAN
NDINetworked (compressed) IP transportEach receiver is another stream to decodeLAN
SRTNetworked contribution/delivery transportPoint-to-point (or via a relay)WAN / internet contribution

They're complementary, not rivals: in our own build, cameras arrive over SRT (internet contribution), land in an MXL domain (production), and the finished program leaves as WebRTC. MXL doesn't replace a contribution transport — it replaces the router and the copies inside the facility. TAMS then handles time-addressed recording.

Where MXL sits: DMF, TAMS and NMOS

MXL is one layer of a larger open stack, all of it vendor-neutral:

  • EBU Dynamic Media Facility (DMF) — the reference architecture / vision. MXL is its data plane.
  • TAMS — the BBC's Time-Addressable Media Store (an Apache-2.0 API specification) for storing and querying segmented media by timerange. MXL grains group naturally into TAMS flow segments.
  • AMWA NMOS — the control plane for discovery and connection; BCP-007-03 defines how MXL flows appear to standard NMOS controllers.
