The control plane

Controlling MXL: AMWA IN-001

MXL defines how media is exchanged — it deliberately doesn't define how an external controller manages the readers and writers doing the exchanging. AMWA IN-001 is the draft that starts to fix that, and it's open for public review right now. If you've built anything that drives MXL, this is the standard to measure yourself against.

Office Hours GlobalSource: AMWA-TV/in-001Draft · Oct 2026

The gap IN-001 fills

Here's the honest architecture, straight from the specs. MXL is the data plane — it moves grains through shared memory. AMWA NMOS (including BCP-007-03) handles discovery and connection. But between those sits a gap: once a controller has found an MXL sender and receiver, how does it operate them — set their parameters, query their status, manage their lifecycle? Per the IN-001 README itself: "MXL does not define a control API," and documenting the requirements for one "promotes interoperability among vendors."

Anyone who has built a working MXL system has already invented an answer to this — including us. Our switcher does, in effect:

browser  →  our REST API  →  MXL readers / writers
            (enumerate, switch, inspect, attach/detach)

Every one of those operations is a candidate control primitive. IN-001 is where they get standardized.

What IN-001 actually is

From the AMWA repository, verbatim:

AMWA IN-001 — in its own words

Title: "API Requirements – Control of the Media Exchange Layer (MXL) v1.0." It "Defines the functional and non-functional requirements for a control API that manages MXL Readers and Writers in a DMF environment" — specifically, requirements for "setting parameters and querying status of MXL Writers and Readers."

Two things make it strategically important right now:

  • It's a draft ("Increment"), not a frozen spec. Its content is explicitly "subject to evolution based on ongoing testing, consensus-building, and community input."
  • They're asking for feedback. "Public review is encouraged! Please post an Issue to the Repo to submit questions, feedback, or propose changes."

That's an open door for anyone with a real implementation. Field data beats opinion in standards work — and field data is exactly what running a live MXL facility produces.

A real control matrix: our switcher vs IN-001

The most useful thing an implementer can do is map their real operations onto the emerging model and see what lines up — and what doesn't. Here's our working browser switcher's control surface against IN-001 concepts:

What our UI doesCorresponding IN-001 conceptNotes from our implementation
Enumerate available sourcesDiscover / query writersWe list flows in the domain; IN-001's status-query requirements cover this.
Switch program input (cut)Reader configurationA cut is re-pointing a reader; the selector's active input is a reader parameter.
Inspect flow / health stateStatus query of writers & readersOur measurement doctrine says what to query — content-uniqueness, not just "is it flowing." A candidate requirement.
Attach / detach a media functionConnection lifecycleOur hardest-won lessons (the reader-lifecycle bug family) live here — lifecycle is where real systems break.
Route a flow between hosts (Fabrics)Remote reader/writer relationshipVia mxl-fabrics-proxy; an inter-host control case IN-001 will eventually need.

The interesting rows are the bottom two. Our field findings on reader lifecycle and honest status measurement are precisely the kind of real-world edge cases a requirements draft benefits from. That's the contribution: not "here's a feature," but "here's what a control API must handle, learned the hard way."

IN-001 vs BCP-007-03 — how they relate

Easy to confuse, so to be clear about what we understand from the public drafts:

  • BCP-007-03 — "NMOS Support for MXL." Establishes how MXL senders/receivers appear to NMOS and how they're connected (an IS-05 transport). This is discovery + connection.
  • IN-001 — requirements for controlling MXL readers/writers once connected (parameters, status). This is operation.

Discovery → connection → control. BCP-007-03 covers the first two for the NMOS world; IN-001 is scoping the third. Together they're the control-plane half of the Dynamic Media Facility.

Why this is an opening, not just reading

The design lesson we'd keep thinnest: treat your own control API as an adapter layer, not the destination. Today's MXL control endpoints (and the fabrics-proxy config) are explicitly expected to evolve toward standardized discovery/connection/control. Build glue you can swap, and you're positioned to adopt IN-001 / NMOS as they solidify — rather than maintaining a bespoke orchestration layer the standard later replaces.
