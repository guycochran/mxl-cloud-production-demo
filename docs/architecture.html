MXL architecture: grains, flows, domains & the ring buffer

A correct, source-grounded explanation of how the Media eXchange Layer actually stores and moves media. Every quote below is from the MXL SDK's own docs (docs/Architecture.md, Timing.md, Addressability.md) — not paraphrase.

New to the vocabulary? The glossary has one-line definitions; this page is the deeper "how it actually works."

The domain — memory as the facility

Per the SDK architecture doc: "The base folder where flows are stored is called an MXL domain. Multiple MXL domains can co-exist on the same host." Concretely, a domain is a directory of memory-mapped files; each flow is a subdirectory, ${mxlDomain}/${flowId}.mxl-flow/. A media function that opens the domain can see every flow in it — which is why, in MXL, the shared memory is the router.

Flows & ring buffers

A flow is "ring buffers stored in memory mapped files" carrying NMOS IS-04 Flow resources. The ring is deliberately small — old grains are overwritten as new ones arrive, because a live production only needs "now" plus a little slack. The SDK provides two ring-buffer types:

  • Discrete — "used for granular data types such as video and ancillary data" (one grain = one frame).
  • Continuous — "used for audio" (a continuous sample stream rather than discrete frames).

Grains & progressive writes

A grain is the fundamental unit of media (a video frame, a block of audio). A subtle but important detail: "Grain I/O can be 'partial'. In other words, a FlowWriter can write the bytes of a grain progressively (as slices for example)."

That's why readers must respect a commit marker. From the docs: "A complete grain will have mxlGrainInfo.committedSize == mxlGrainInfo.grainSize. It is imperative that FlowReaders always take into consideration the mxlGrainInfo.committedSize field before making use of the grain buffer." Ignore it and a reader can consume a half-written frame — exactly the kind of torn read that shows up as corruption on air.

The timing model — TAI, no PTP required

This is the piece that makes multi-host MXL elegant. Grains aren't positioned by queue order — they're positioned by time. Each ring index corresponds to a timestamp relative to the PTP epoch as defined by SMPTE 2059-1, using TAI time. But crucially:

From the timing doc

"MXL does NOT require a PTP/SMPTE 2059 time source: it only leverages the epoch and clock definitions (TAI time)." For multi-host setups, "MXL requires that the time source of these hosts does not slip against each other over time" — any stable, non-drifting clock (ordinary NTP, in our experience) is enough.

The indexing is pure arithmetic:

GrainDurationNs = GrainRateDenominator × 1,000,000,000 / GrainRateNumerator
GrainIndex      = Timestamp / GrainDurationNs
RingBufferIndex = GrainIndex mod RingBufferLength

The payoff, which we measured directly: if two hosts share a clock, a flow arriving from another machine lands at the same index its local peers do — so a switcher reads a remote camera exactly like a local one, no manual latency offset. The field proof →

Reader/writer synchronization

One implementation choice with a real operational consequence: "Synchronization between readers and writers is performed using futexes and not using POSIX mutexes, which would require write access to the mutex stored in shared memory." Using futexes means readers can mount the domain read-only — which is exactly what you want when many containers consume a flow but must never be able to corrupt it.

Addressing a flow

Flows have a URI form: mxl://<authority>/<domain-path>?id=<flow-uuid>. The UUID is the NMOS IS-04 flow id, which is how MXL ties into the NMOS control plane (discovery, routing) without the data plane having to know anything about it.

Why this design is clever

Put the four ideas together and the elegance shows:

  • Ring buffers in shared memory → extra consumers are nearly free (zero-copy fan-out).
  • TAI-indexed grains → position is a timestamp, so clock-synced hosts align automatically — no sequence negotiation.
  • Progressive writes + a commit marker → low latency (readers can follow a frame as it's written) without torn reads.
  • Futex sync + read-only mounts → safe, high-fan-out consumption that can't corrupt the source.

None of it is exotic — it's careful systems engineering applied to media. That's the whole appeal: a facility built from these primitives is software you can reason about, not a chain of boxes you have to re-cable.
